# Версии: как пускаме 1.0, поправки 1.0.x и после 2.0

Кратко: **не се клонира проектът**. Работим в същото репо в GitHub, а версиите се пазят с **тагове** и **клонове** (branches) в git. Всяка пусната версия може да се извади точно такава, каквато е била, по всяко време.

## Номерата

`ГОЛЯМА.МАЛКА.ПОПРАВКА`, например `1.0.0`:

- **1.0.1, 1.0.2…** – само поправки на бъгове. Нищо ново за играча.
- **1.1, 1.2…** – нови неща, които не чупят нищо: нови карти, нови лиги, по-добър интерфейс. Записите продължават.
- **2.0** – голяма промяна: ново правило в мача, преработена кариера, нов вид игра. Записите се обновяват с миграция (с резервно копие), ако може. Ако не може, казваме го честно.

Номерът се сменя в `server/Directory.Build.props` (`<Version>`).

## Пускане на 1.0.0

1. **Тестване.** Всичко е проверено, тестовете минават, пакетът е тестван на друг компютър.
2. **Таг.** В git се слага „етикет“ на точно това състояние:
   ```powershell
   git tag -a v1.0.0 -m "Dugout Deck 1.0.0"
   git push origin v1.0.0
   ```
3. **Release в GitHub.** Там (Releases → Draft a new release → таг v1.0.0) прикачвате zip-а `DugoutDeck-1.0.0-win-x64.zip` и кратък списък с новостите. Така винаги имате точния пакет, който е качен в itch.io.
4. **Клон за поправки:**
   ```powershell
   git branch release/1.x v1.0.0
   git push origin release/1.x
   ```

## Докато хората играят 1.0, ние работим по 2.0

- **`main`** е мястото за новата работа (бъдещата 2.0). Тук продължаваме както досега.
- **`release/1.x`** е само за поправки на пуснатата версия.

**Поправка на бъг в 1.0** (напр. играта засяда):
1. `git switch release/1.x`
2. оправяте, сменяте версията на `1.0.1`, commit;
3. таг `v1.0.1`, пакет, качване в itch.io (играчите си обновяват);
4. същата поправка се пренася и в `main`, за да я има и в 2.0:
   ```powershell
   git switch main
   git cherry-pick <номерът на commit-а с поправката>
   ```

**Когато 2.0 е готова:** в `main` сменяте версията на `2.0.0`, таг `v2.0.0`, нов пакет, качване. После клон `release/2.x` за поправките на 2.0. Старият `release/1.x` просто остава в историята.

## Записите на играчите

Това е най-важното при нова версия:
- Записите са в `%LOCALAPPDATA%\DugoutDeck`, не в папката на играта, така че обновлението не ги трие.
- При промяна на базата правите миграция (виж README → „Промяна на базата“). Новата версия сама обновява стария запис и прави резервно копие `dugout-deck.db.backup-<дата>`.
- Ако 2.0 променя мача така, че недоиграните мачове от 1.0 не могат да продължат, те се изтриват при стартиране (`MatchState.CurrentVersion`). Кариерите остават.
- **Не триете стари миграции.** Те са „стълбата“, по която всеки стар запис се качва до новата версия.

## Защо не клониране

Ако копираме проекта в нова папка за 2.0, всяка поправка трябва да се прави на две места и копията бързо се разминават. С тагове и клонове историята е една, всяка версия може да се възстанови с `git switch --detach v1.0.0`, а поправките се пренасят с една команда.
